# TP2 : Le serveur et l'intégration

<Row>

<Column>

Les deux apps parlent maintenant au **même** serveur Spring Boot. Plus rien n'est factice : les données viennent du serveur et y sont sauvegardées (H2 en local pour ce TP).

:::info Le contrat commun

Le professeur fournit `API.md` : les routes, les DTO et les codes d'erreur, **identiques pour toute la classe**, ainsi qu'une collection Bruno de vérification.

Pourquoi un contrat commun? Ton app doit pouvoir parler au serveur d'une autre équipe, et pendant le [CTF](../cours/ctf), les autres équipes attaqueront **ton** serveur avec les mêmes routes.

:::

:::info IA

- <Etiquette type="main" /> Les règles d'accès (`serveur/ACCES.md`) et la relecture (`serveur/RELECTURE.md`) sont écrites à la main.
- <Etiquette type="claude" /> Le serveur et l'intégration Retrofit des deux apps sont produits avec Claude, en respectant `API.md`.
- Voir [Spring par Claude](../cours/spring-par-claude).

:::

</Column>

<Column>

:::note Dépôt Git &#8203;<Highlight color="tip">2 points</Highlight>

Le serveur dans `serveur/`, les apps dans `android/`, dans le même repo. Commits réguliers.

:::

:::info Règles d'accès &#8203;<Highlight color="tip">2 points</Highlight>

`serveur/ACCES.md`, écrit **avant** de générer le serveur : pour chaque route, **qui** a le droit (enseignant du groupe, étudiant concerné, collègue, personne) et le code renvoyé sinon (401, 403, 404). Exemples de règles :

- un étudiant ne voit **que ses** notes;
- seul l'enseignant du groupe crée une évaluation ou saisit une note;
- une révision est demandée par l'étudiant concerné, proposée par l'enseignant du groupe et validée par un **autre** enseignant.

:::

</Column>

</Row>

## Livrables

<Row>

<Column>

:::info Serveur &#8203;<Highlight color="tip">4 points</Highlight>

- Rôles enseignant / étudiant, connexion par session (cookie).
- Toutes les routes de `API.md`; la collection Bruno du professeur passe.
- L'identité vient **toujours de la session**, jamais d'un paramètre envoyé par le client.
- Moyenne pondérée calculée par le serveur.
- Déclaration des notes finales d'un groupe au **Dossier scolaire** (système légacy fourni), avec gestion de la panne, de la lenteur et de la double déclaration ([système légacy](../cours/systeme-legacy)).
- Tests JUnit : moyenne pondérée, workflow de révision (dont « un enseignant ne valide pas sa propre proposition »).

:::

</Column>

<Column>

:::info Intégration &#8203;<Highlight color="tip">4 points</Highlight>

- Tous les écrans des deux apps utilisent le serveur.
- Les erreurs (réseau, 403, note invalide…) s'affichent clairement, dans les 6 langues ([erreurs GUI](../cours/erreur-gui)).
- Un indicateur d'attente pendant chaque appel ([attente serveur](../cours/attente-serveur)).

:::

:::info Relecture &#8203;<Highlight color="tip">2 points</Highlight>

`serveur/LEGACY.md` (exercice 1 de [système légacy](../cours/systeme-legacy)) et `serveur/RELECTURE.md` : trace d'une demande de révision de bout en bout, instances après 30 requêtes, origine de l'identité, test inutile repéré ([Spring par Claude](../cours/spring-par-claude), exercice 3).

:::

</Column>

</Row>

## Défense à la main &#8203;<Highlight color="tip">6 points</Highlight>

<Etiquette type="main" /> Sans IA, 10 minutes :

- tracer au tableau une action choisie par le professeur, de l'appui sur le bouton à l'affichage, en nommant à chaque étape le fichier et la fonction :
  1. **client, avant** : le code qui s'exécute quand l'action est déclenchée (lambda, appel du service Retrofit);
  2. **requête** : méthode, URL, en-têtes (dont le cookie de session) et corps JSON;
  3. **serveur** : le code qui se déclenche (contrôleur, service, dépôt) et d'où vient l'identité;
  4. **réponse** : code HTTP, en-têtes et corps JSON, y compris pour un cas d'erreur (403, 404);
  5. **client, après** : le code qui reçoit la réponse et ce qui change à l'écran (état, recomposition, message d'erreur);
- dire combien d'objets de chaque classe serveur existent après N requêtes;
- montrer, dans le code, où est vérifiée une règle de `ACCES.md` choisie par le professeur, et la modifier devant lui.

Un TP que tu ne peux pas expliquer voit sa note plafonnée à la note de défense.
